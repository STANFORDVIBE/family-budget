# Архитектура Family Budget

Десктопное приложение Windows на **Tauri 2**: финансовое ядро и база — в Rust, интерфейс — React в WebView2.
Данные хранятся локально в SQLite, интернет не нужен.

## Слои

```
React (src/)                      Presentation: экраны, формы, графики. Денег не считает.
  │  invoke("command", {...})     Типизированный IPC (src/lib/api.ts ↔ src-tauri/src/commands)
  ▼
commands/   (Rust)                Тонкий слой IPC: десериализация, вызов сценария, диалоги выбора файлов.
app/        (Rust)                Application: сценарии (создать операцию, перевести, восстановить копию...).
                                  Каждая запись — одна транзакция SQLite вместе с журналом и sync-метаданными.
domain/     (Rust)                Domain: чистая финансовая логика без БД и UI — деньги, курсы, проводки,
                                  расписания платежей, бюджеты, цели, контракт синхронизации.
db/         (Rust)                Infrastructure: подключение SQLite, прагмы надёжности, миграции, справочники.
```

`domain` не знает ни про SQLite, ни про Tauri, ни про React и полностью покрыт unit-тестами.
`app` покрыт интеграционными тестами на настоящей SQLite (`src-tauri/src/app/scenarios.rs`).

## Деньги

- Суммы — только целые минимальные единицы (`i64`: центы, копейки). Число знаков — из справочника валют
  (JPY — 0, BHD — 3).
- Курсы — точные десятичные дроби (`Rate`: мантисса `i128` / 10^scale), хранятся строкой `"97.45"`.
- Конвертация — целочисленная, округление «половина от нуля», переполнение — ошибка, а не тихий перенос.
- В интерфейсе суммы вводятся и выводятся строковыми операциями (`src/lib/money.ts`), `parseFloat` запрещён линтером.

## Проводки и балансы

Каждая операция — заголовок (`transactions`) и проводки по счетам (`transaction_entries`) со знаком:

| Тип           | Проводки                                                        | В аналитике        |
|---------------|-----------------------------------------------------------------|--------------------|
| Расход        | `−сумма` на счёт                                                | расход             |
| Доход         | `+сумма`                                                        | доход              |
| Возврат       | `+сумма`, категория расхода                                     | уменьшает расход   |
| Перевод       | `−сумма` со счёта, `+сумма` на счёт (+ отдельная `fee`)         | только комиссия    |
| Корректировка | `±разница` до фактического баланса                              | не учитывается     |

Баланс счёта не хранится: `начальный баланс + SUM(проводок)` проведённых, неудалённых операций.
Поэтому он всегда совпадает с историей и восстанавливается из неё.

Каждая проводка хранит сумму в валюте счёта **и** в основной валюте пространства по курсу на дату операции.
Аналитика складывает только суммы в основной валюте, поэтому новый курс не меняет историю, а разные валюты
не складываются без конвертации. Нет курса — операция не сохранится (`rate_missing`), интерфейс попросит курс.

## Пространства

Личное и семейное пространство — `workspaces`. У каждой финансовой сущности есть `workspace_id`, каждая команда
получает `workspaceId`, и все чтения/записи фильтруются по нему (`app::ensure_in_workspace`). Счёт или категорию
одного пространства нельзя использовать в другом — это покрыто тестами.

## Надёжность

- SQLite в режиме WAL с `synchronous=FULL`, внешние ключи включены.
- Сценарий записи = одна транзакция: операция + проводки + журнал + sync-метаданные, всё или ничего.
- Мягкое удаление (`deleted_at`) — удалённую операцию можно вернуть; категорию с историей нельзя удалить без
  переназначения; счёт с историей — только в архив.
- Идемпотентность: интерфейс генерирует UUID операции заранее, повторная отправка не создаёт дубль.
- Регулярные платежи никогда не списываются сами: создаётся ожидающая операция; уникальный индекс
  `(recurring_rule_id, recurring_occurrence)` не даёт создать её дважды.
- Резервные копии — полная копия SQLite через online backup API, с проверкой целостности; перед восстановлением
  автоматически сохраняется текущее состояние.

## Готовность к облаку

Модель local-first: облако в будущем не заменит локальную базу, а будет синхронизироваться с ней. Поэтому вместо
подмены репозиториев заложено:

- UUID v7 для всех записей, `version` + `updated_at` + `deleted_at` у каждой синхронизируемой строки;
- `sync_metadata` — какие строки изменились локально (dirty) и какая версия была синхронизирована;
- `domain::sync::SyncProvider` — контракт push/pull; в текущей версии стоит `LocalOnlyProvider`, который ничего не отправляет;
- `domain::sync::compare_versions` — обнаружение конфликтов (изменено с обеих сторон);
- `users` и `workspace_members.user_id` — точка подключения облачных аккаунтов и ролей.

Как подключить облако, когда понадобится:

1. Реализовать `SyncProvider` (push/pull по HTTP) — финансовая логика и UI не меняются.
2. Push: строки с `sync_metadata.dirty = 1` → `ChangeRecord`; принятые — `dirty = 0`, `synced_version = local_version`.
3. Pull: применять чужие изменения через те же сценарии `app/`, чтобы сохранялись проверки и журнал;
   конфликт (`compare_versions` → `Conflict`) показывать пользователю, а не перезаписывать молча.
4. Вход в аккаунт связывает локального `users` с облачным; приглашённые в семью — через `workspace_members.user_id`.
5. Токены — в хранилище учётных данных Windows, не в базе и не в файлах.

## Безопасность

- WebView не имеет доступа к файлам, shell и сети: в capabilities только базовые права окна, строгая CSP.
- Все входные данные проверяются в Rust (типы — serde, значения — `app`/`domain`); SQL только с параметрами,
  имена таблиц — из закрытого списка.
- Пути к файлам выбираются только системным диалогом на стороне Rust или берутся из папки бэкапов по имени
  файла без разделителей пути.
- Ошибки, уходящие в интерфейс, содержат только код и безопасную деталь (поле, валюту), без SQL и путей.
- Финансовые данные не логируются и никуда не отправляются.
- Единственный выход в сеть — проверка обновлений по кнопке (`commands/update.rs`, из Rust, не из WebView):
  `latest.json` с GitHub Releases и установщик, подпись которого сверяется с ключом в `tauri.conf.json`.
  Перед установкой делается резервная копия `before-update-*`.
